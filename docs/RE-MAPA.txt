==================== player-car
SUMMARY: I traced the local player's car from the main loop down to the physics body; the full pointer chain is below. To get the car for player i: idx = GetLocalPlayerIndex() (0x2694D0, returns 0 when not in a network game), then player = *(0x558814 + 8 + 4*idx), vehicle = player+0x14, car = vehicle+0x08.

What hangs off the vehicle and the car:
- vehicle+0x04 is the input object (mcPlayerInput, vtable 0x47684C).
- vehicle+0x1C is the phInst. Its world matrix is a packed 4x3 at +0x10, and the position is at +0x34.
- car+0x68 is the collider, and collider+0x10 is the rigid body (vtable 0x4A33F8). On the body, linear velocity is at +0x44, angular velocity at +0x50, and its own copy of the 4x3 matrix at +0x5C (position at +0x80).
- Speed is stored on the car at +0xB0 (length of the body's velocity).
- The control fields on the car are steer +0x6C, throttle +0x70, brake/reverse +0x74, handbrake +0x78, flags +0x7C. The input update writes them every frame.

Teleport / reset: write the spawn position to car+0x80 (0x3305F0), the rotation angles to car+0x8C (0x330610; the game uses (0, heading, 0)), and the starting velocity and spin to car+0x98 and car+0xA4. Then call the car's virtual Reset (vtable slot +4, which is 0x124520 and then 0xA2460). The game also has a snap-to-ground helper (0x122770), and the player-level wrappers are 0x2C8860 (set start position), 0x2C8690 (reset to start) and 0x2C19B0 (mcPlayer::Reset, used for the cruise reset).

Per frame: main() at 0x12440 calls the main loop 0x1F9D0, which switches on the game state stored at [0x557ED0]+4. The game update 0x1EDB0 then calls:
- the physics simulator 0x29D210 on [0x558120], which runs N substeps (frame time is the float at 0x4B2D48);
- the player manager update 0x2BDEC0 on [0x558814];
- the player manager in turn calls the vehicle manager [0x5638E4], whose update 0xFEF80 copies each car's matrix to its model.
Car update is 0xFFD90 and input update is 0x2C9AA0.

The game already has system-link netcode for this input. In a network game (config+0x108 set) the controls are packed into 8 bytes (input+0x6C to +0x77). Remote cars are then driven from that packet by 0x2C9570.

==================== car-config
SUMMARY: The game describes a customized car with one 0x108-byte class that names itself "CarCfg" (vtable 0x4483DC, ctor 0x271D20, copy 0x271E20 with thunk 0x272010). Its reflection/registration function 0x270E80 names every field. CarCfg+0xE3 holds the model name (TypeName, char[0x16]). The rest of the struct holds parts indices (rims, bumpers, body, spoiler, hood...), paint (type, preset, 5 colour XYA + colour-shift), vinyl, logos/decals, chrome/neon/tint colours, performance levels (EngineState0-6, Trans, Suspension, Brake, Tire, Hydraulics) and tuning (camber, ride height, tire width/offset/profile, rim size).

The live career profile is a static object at 0x53F308. It has 30 owned-car CarCfg slots at 0x53F810 (+0x508, stride 0x108), the owned-car count byte at 0x53F80C (+0x504) and the currently selected garage slot byte at 0x53F80D (+0x505). Per-model stock CarCfgs start at 0x541700 (+0x23F8); there are 127 in the Remix layout. The save copy lives at mcMemCard(0x4CB690)+0x14.

Races are built from a "race setup" object (0x3E0 bytes, ctor 0x26B9E0). There are three globals of this type: 0x53F2E0 (active), 0x53F2E4 (lobby/network) and 0x53F2E8. Each has 8 player entries at +0x114 with stride 0x2C, and entry+0x0C points to that player's CarCfg (absolute: [setup + slot*0x2C + 0x120]). 0x268FF0 copies 0x53F2E4 into 0x53F2E0. The player manager 0x2BE100 then constructs each player (0x2BFE50). That ctor fills an mcPlayerFactory descriptor (0x2CB270, vtable 0x476940; base ctor stores CarCfg* at +0x54) and calls 0x2CBC40. 0x2CBC40 allocates an mcCarCustom (0x3138 bytes, ctor 0xF4430) and applies the CarCfg with 0xF32A0.

The game's own netcode already sends the whole CarCfg, raw. There are two messages:
(1) The join/player-info message: base type 0x04, 0x198 bytes, CarCfg at +0x88. The client builds it in 0x2EFF0 from setup slot 0. The lobby picks that car through 0x155920, which by default takes the CAREER garage's current car. The host's join handler 0x2EC80 stores it in [[0x53F2E4] + assignedSlot*0x2C + 0x120].
(2) The car-config update message: type 0x44, 0x114 bytes, CarCfg at +0x08, slot at +0x110, flag at +0x111. It is sent by 0x25D20 (session vtable 0x449100, slot +0x13C) and received by 0x26370 (+0x1A0, through dispatcher 0x1AF470). The host relays it to everyone else and each peer copies it into the same per-slot CarCfg.

So the partner's own campaign car (model, parts, paint, vinyls, upgrades, tuning) can travel through the existing path unchanged. A co-op mod has to make sure the partner side picks from the career garage (0x53F2FC == 0). It also has to put the received CarCfg into an active slot of the host's race setup before 0x2BE100 or 0x2BFE50 runs.

==================== race-career
SUMMARY: I mapped the career race flow statically, from opening a race in cruise through the race state machine and checkpoints to applying the result to the career.

Key objects:
- Global 0x557F0C is the mcPgCareer object (ctor 0x278160, vtable 0x473B98). Its fields: +0x0C careerData (0xCC8 bytes), +0x10 unlock/progression manager, +0x14 rewards.
- 0x557EEC is the mcRaceStateDerived state machine (vtable 0x4691B8).
- [0x533E24]+4 is the current race object (mcRaceBase family; base vtable 0x46A010).
- 0x53F2E4 and 0x53F2E0 are the 0x3E0-byte next and current game-setup structs.
- 0x557EE4 is the static per-city race database.

Starting a race: in cruise, the hookman logic (0x1D8F20) finds the player inside an open race's start marker and calls mcPgCareer::StartRace(u16 UniqueId) at 0x277990. SetupNextCareerRace (0x278270), state 4, then calls the race-setup function 0x277AE0(UniqueId). That function looks up the open-race record, sets careerData+0x58 = current race id, and fills the next setup via 0x26B8E0(City, RaceIdx). Progress (0x2779D0) then commits the state and switches the game state machine (8, then 6) so the race loads.

Race states (EnterState 0x1C3B70, jump table 0x1C3C28):
- 2: intro
- 4: countdown
- 5: GO
- 7: finished
- 12: race over

On entering state 7 (0x1C2B00) the game does three things in order:
1. Awards money once, based on finishing position (0x1CFC50).
2. Computes result = localRacer.won ? 0 : 1.
3. Calls 0x1D1810(result), which in career mode calls mcPgCareer::ReportRaceResult(result) at 0x277EE0.

Result codes: 0 won, 1 lost, 2 changed vehicle, 3 restart, 4 quit to cruise, 5 quit to front end, 6 end of race to garage.

On a win, with career state 4 and no tournament flag, ReportRaceResult calls 0x277530. That function:
- erases the race from the open-race list and adds it to history;
- increments NumberOfWonRaces;
- advances the hookman counter (which can mark the hookman as beaten);
- applies the side-quest or filler reward.
It then runs the unlock evaluation 0x2893C0.

The race UniqueId is a per-save counter (careerData+0xB18 "UniqueRaceIdCounter"), so it is NOT stable between two copies. A stable cross-copy key is (City, RaceIdx), i.e. record bytes +0x08 and +0x06. The setup race-name string (setup+0x68) also works, and the existing online code already uses it to tell "next race" from "restart".

To force or credit a win:
- Set the local racer-info +0x5D (won) to 1 before race state 7 is entered (or push 0 at 0x1C2B52), or
- Call ReportRaceResult(0) while career state is 4 and careerData+0x58 holds the race's local UniqueId.

The race must exist in the local open list: 0x277530 does not check for index -1.

==================== ai-traffic
SUMMARY: Map of the AI opponents, traffic and multiplayer car slots (static analysis only). Addresses are VAs. Code starts at 0x10000, so functions sit around 0x0001xxxx–0x0037xxxx.

KEY RESULT FOR THE CO-OP: AI opponents and human players are built through the same car factory into the same vehicle class. Base factory 0x361B30 makes a 0x3138-byte car with ctor 0xF4430, then applies a 0x108-byte car record with 0xF32A0, which sets tuning, parts, paint and the plate. The only difference is where the car record comes from:
- AI: race descriptor +0x64.
- Player i: game-settings slot i +0x120 (a pointer to a 0x108-byte record that the settings object owns).

The game's split-screen (2 local players) and network modes (up to 8, mask from the session object 0x557EFC) already create one full player object per settings slot, each built from that slot's record. So the cleanest way to show the partner's own campaign car is:
- put the partner's garage record into slot 1 +0x120 (copy with 0x271E20, like 0x268E50 does);
- set players = 2 at settings+0x4C;
- let the player manager build it.

The local garage is an array of 0x108-byte records at 0x541700, the same format as the slot record.

POOLS:
- Players: 8 settings slots and 8 player-manager slots.
- Split-screen: at most 2.
- Racer list at 0x558838: 10 pointers. Players plus competitive AI must be 10 or fewer; nothing checks the bound.
- Non-competitive AI per race-list entry: 4.
- Opponent name pool: 61 names (Tokyo has its own 30).
- Traffic: no fixed number in code. The count comes from the city's "_traffic" resource (traffic manager +0x12C), with 0x21C-byte entries.

Rubber banding is computed per AI from distance thresholds and throttle limits set in the race file. Which human it measures distance to was not found.

==================== save-progress
SUMMARY: I mapped how the career is saved and what a race win changes. Everything comes from static reading of the generated asm comments and default.xbe; nothing was run.

Globals:
- [0x557F0C] = mcPgCareer*.
- [mcPgCareer+0x0C] = career data object, the part that is serialised. It holds money at +0xACC, the current city at +0x50, the open-race list at +0xA58, the won/skipped counters at +0xA78/+0xA7A, and the 'Beaten' flags of hookmen at +0xAA0.
- 0x53F308 = global profile/config block of 0x18340 bytes, copied whole into the save. It holds the garage: owned-car count is the byte at 0x53F80C (max 0x1E = 30), the selected car is the byte at 0x53F80D, and the car records start at 0x53F810 with a stride of 0x108.
- [0x4CB690] = the mcMemCard singleton. Its state is at +4: 10 = save a new profile, 100 = save the current profile, 120 = save variant (GUESS), 130 = load, 140 = cancel. mcMemCard::Update is 0x1A9E0 and is pumped every frame from 0x1F9D0.

The game's own save flow: `ecx=[0x4CB690]; push 0,0,0,0,1; call 0x19360`. It only works if a profile is loaded (byte [memcard+0x334B4] != 0). On the next Update, 0x1A550 serialises the profile and the career into the memcard buffer and calls 0x22040, which writes save game "Remix : <profile>", file "<profile>.mc3Remix".

Race end:
- mcRaceStateDerived (vtable 0x4691B8) state 7 runs 0x1C2B00. It awards prize money (0x1CFC50: money += prize) and then calls 0x1D1810, which calls mcPgCareer::ReportRaceResult (0x277EE0) with result 0 = won, 1 = lost.
- A win with career sub-state [pgCareer+0x24]==4 calls 0x277530. That moves the race out of OpenRaces (CloseRace 0x281130, which increments NumberOfWonRaces), can mark a hookman beaten (0x281370), updates the per-city beaten table and sets the dirty byte [pgCareer+0x20]=1.
- Then race state 11 (0x1C33E0) autosaves through 0x19360 when the career dirty flag or the garage dirty flag (0x557648) is set.
- Career credit and autosave are both skipped when [0x53F2D4] != 2 (not career mode) or when mcGameState ([0x557ED0]) +4 == 3. State 3 is very likely replay playback (GUESS).

The debug career log "%sMC_Career_log_%s.txt" is dead in this retail build. Two functions format it into a stack buffer with "c:\\" and the profile name, and the buffer is never used. Nothing logs to it, so progress has to be watched through the fields below.
