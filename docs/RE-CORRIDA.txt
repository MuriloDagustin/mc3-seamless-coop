==================== race-start
RECIPE: HOW A CAREER RACE STARTS IN CRUISE (static, all asm seen):
- Pressing a button does not start a race, speed is not checked, and no "Start race?" prompt appears. The race starts as soon as the local player's car is inside a start marker that is "armed". The cruise object is the careercruise class (vtable 0x46A7D8, [[0x533E24]+4], setup type [[0x53F2E0]+0x18]==1 'find_hook'). Every frame its Update 0x1D8F20 (vtable slot +0x34) walks every open-race record i in careerData ([cruise+0x1320] == [[0x557F0C]+0x0C]) list +0xA5C..+0xA60 (stride 0x4C). It keeps the records that pass the filter below and gives each kept record the next marker slot s (s = 0,1,2..). For each kept record it calls 0x1D71C0(i,s), which copies the start position from the race database into checkpoint slot s and writes the record's UniqueId to u16 [cruise+0x1300+s*2]. It then calls 0x1D1550(player, s, 0, 0), which runs the crossing test 0x1CF8B0. When the test hits, the game runs these steps:
  1. 0x1D6750("Prepare_To_Race"): sound 0x21, HUD text, local racerInfo +0x04=1 and +0x5D=1, then race state machine EnterState(7). 0x1C2B00 then calls 0x1D1810(0) -> ReportRaceResult(0), which is harmless in the cruise career state.
  2. mcPgCareer::StartRace(rec.UniqueId) 0x277990 sets pgCareer+0x2C=4 (next state = race), pgCareer+0x34=UniqueId (u16), pgCareer+0x30=rec.City and pgCareer+0x20=1, then notifies listeners.
  3. Sets cruise+0x0D=1.
  Then race state 7 waits 3.1 s (float [0x469230]). 0x1C2010 is true for type 1, so the machine goes to state 11 (autosave; it waits while state-machine +0x14 is set), then state 12. The state 12 Update (0x1C3A84, setup+0x18 in {1,3}, +0x26==0, +0x4C==0) calls SetupNextCareerRace 0x278270 -> 0x277AE0(pgCareer+0x34). That fills [0x53F2E4] with setup+0x00=City and setup+0x68=race name (via 0x26B8E0) and sets careerData+0x58=UniqueId and careerData+0x50=City (0x2806F0). It then calls Progress(0) 0x2779D0, which copies +0x2C into +0x24, puts game state [0x557ED0] to 8 then 6 (load), and clears pgCareer+0x34.
FILTER (all must hold, in 0x1D8F20): rec.City s8 +0x08 == [[0x53F2E0]+0x00]. rec.Hookman s8 +0x09 == -1, or that hookman is not in the roaming-challenger list cruise+0x12DC (stride 0xC, count +0x12FC). rec.Class s8 +0x0A < 0, or == class of the local car ([[0x557EB0] + [[player+0x10]+4]*0x28 + 8]). cruise+0x1258 < 0 and cruise+0x125C < 0 (no AI challenge/follow in progress). cruise+0x0D == 0. car flag [[[player+0x14]+0x0C]+0x132] != 0. cruise+0x1250 (armed) != 0. Here player = [[0x558814]+8+4*idx] with idx = 0x2694D0() (normally 0).
ARMING: 0x1D7660 (reset) clears cruise+0x1250. Each frame in which the car is inside no marker sets it to 1 (0x1D91E1). So after a spawn you must leave the markers and come back in.
CROSSING TEST 0x1CF8B0 (cp = [cruise+0x28] + s*0x120, pos = [[player+0x14]+0x1C]+0x34, the same phInst position the mod's car::Place writes): (cp.x-pos.x)^2 + (cp.z-pos.z)^2 <= (cp+0x110 + 0.9)^2 and -1.0 < pos.y - cp.y < cp+0x108 (300.0).

RECIPE: Notation: race = [[0x533E24]+4]. entry(i) = race+0x98+i*0xB8, so local = entry(0) and partner = entry(1). GetLocalPlayerIndex is 0 when setup+0x108 = 0. KEY FACT: EnterState(7) runs synchronously inside the finish call of the LAST human to finish in this world. The chain is 0x1DF8B0 -> 0x1E06E0 -> RequestState 0x1C22D0 -> EnterState 0x1C3B70 -> 0x1C2B00, which reads [race+0xF5]. So no thread can write anything between the last finish and the read. All writes must happen before the last human finishes in this world, and the race only ends on a real game finish event. Nothing ever re-checks race+0x1250 later in a way that enters state 7.

(a) Partner won, so this copy must report 0 (won):
1. When the partner reports "I won" (or this world's partner car got entry(1)+0x5D = 1), and while [0x557EEC]+4 is 5 or 6, write byte [race+0xF5] = 1 (local entry+0x5D).
2. This works before or after the local player crosses the line:
   - Before: when the local player finishes, 0x1DF94A writes +0x5D = IsWinner(0) (0x1DF0A0). IsWinner returns 1 at once when its own +0x5D is already 1 (0x1DF0D8), provided entry+0x07 [race+0x9F] != 0 (set to 1 at reset, cleared only by the elimination classes). So the preset survives.
   - After the local player finished but while the partner car in this world has not (race+0x1250 = 1, state 6): nothing rewrites it.
3. Then 0x1C2B44 sees 1, pushes 0, and 0x1D1810 calls ReportRaceResult(0). It also makes the local finish banner rw_1_pl and the results flag HUD+0x220 (0x1C3540) consistent.

==================== open-race
RECIPE: DATA-ONLY INJECTION OF THE HOST'S RACE INTO THE PARTNER'S OPEN LIST (run in the partner's copy, from the mod thread)

Network key: send (City = rec+0x08, RaceIdx = rec+0x06) plus the host's whole 0x4C-byte record. Do not send the host's UniqueId. UniqueId is a per-save counter, so the same number names a different race in the partner's save.

0. Read the pointers.
   - cd = [[0x557F0C]+0x0C]
   - begin = [cd+0xA5C], end = [cd+0xA60], capEnd = [cd+0xA64], n = (end-begin)/0x4C
   - Re-read begin, end and capEnd every time. The game can reallocate the buffer through 0x2823C0 when it is full.

1. Reuse first. Scan i < n for byte[begin+i*0x4C+0x08] == City and u16[+0x06] == RaceIdx.
   - If a record matches, use its u16[+0x04] as the id and skip to step 6. Nothing gets injected.
   - Optionally also scan PutAside: begin [cd+0xA6C], end [cd+0xA70], stride 0x50, same layout in the first 0x4C bytes. StartRace's 0x276F50 can find put-aside ids, but SetupCareerRace 0x277AE0 and 0x277530 only search the open list, so a put-aside match is not enough. Inject in that case.

2. Check capacity: capEnd - end >= 0x4C.
   - The careerData ctor reserves 130 records ('002836A2 mov ecx,edi(=cd+0xA58); push 0x82; call 0x281F10' = reserve).
   - Reset (0x2827C0 -> 0x282320 resize(0)) and erase (0x280DA0) keep that capacity, so spare room is normally large.
   - If there is no room, abort. A reallocation cannot be done data-only.

3. Build the record in a local 0x4C buffer from the host's bytes, then fix these fields:
   - +0x00 = 0x473E74 (vtable). Required: the slot past end has the base vtable 0x473E44 that the erase destructor 0x27C950 wrote.
   - +0x04 = newId:
     - id = u16[cd+0xB18] + 1; if id == 0, id = 1 (same as 0x2832B3..0x2832C4).
     - Write u16[cd+0xB18] = id.
     - Check that id is not in the open list or the put-aside list, plus [mcPgCareer+0x34] and u16[cd+0x58].
   - +0x09 HookmanIdx: set it to -1 (0xFF) unless the partner's OpenHookmen vector holds (City, Hookman).
     - That vector: begin [cd+0xA94], end [cd+0xA98], stride 0x10, dword city at +0x04, s16 hookman at +0x08 (search 0x27F110).
     - If it is missing, 0x277530 calls 0x27F0F0(-1) and increments byte [[cd+0xA94]-0x10+0x0C]. That is a write before the array (memory corruption).
   - +0x0A SideQuestIdx: set it to -1 unless the partner has that side quest open. 0x283970 does inc/dec on fixed per-city counters at [sqMgr+0x36+sq*7+city*2], which would underflow.
   - +0x1E TaskType: keep it, or set 0.
   - +0x20 Task* (a heap pointer; the task name is at object+0):
     - Set 0, or resolve the host's task name in the partner's own list at [[cd+0x10]+0x5C .. +0x60] (array of object pointers, compared like 0x278C60).
     - Never copy the host's pointer.
   - Result with +0x09 = -1, +0x0A < 0 and +0x1E = 0: 0x27D170 classes it as a filler race. The win then also bumps NumFillerRacesWon dword [cd+0xA7C+City*4] (0x28C790).
   - Keep the rest as sent so opponents and difficulty match the host: +0x0B, +0x0C..+0x18, +0x1C, +0x24 Flags (bit 0x04 is an announce flag, may be cleared), +0x25 CareerOrder, +0x26 NumOpponents, +0x27, +0x28 PrizeMoney, +0x2C, +0x30, +0x34..+0x4B opponent configs.

4. Publish it.
   - memcpy the 0x4C bytes to [end].
   - Then do one aligned dword write [cd+0xA60] = end+0x4C, last (the record is complete before it becomes visible).
   - Do this while the partner is idle in cruise or the front end. Do not do it while the game itself may push_back (end of race, the unlock evaluation 0x2893C0, the put-aside reopen 0x283370).

5. Optional, mirrors a natural open in 0x283260: u16[cd+0x5A + (City*0xA0 + RaceIdx)*2] += 1 (LongTermRaceInfos, which is saved).

6. Start the race with this copy's id.
   - The cruise marker calls StartRace(rec+0x04) itself; or replicate StartRace 0x277990: [pg+0x2C]=4, [pg+0x34]=(u16)id, [pg+0x30]=City, [pg+0x20]=1. StartRace also calls 0x279430/0x277930/0x277140, which a data-only write skips.
   - SetupCareerRace 0x277AE0 then sets u16 cd+0x58 = id and u16 cd+0xA8C = the index (0x27DB00). It has NO -1 check, so the record must exist.

7. Win (either player wins: force ReportRaceResult(0)).
   - 0x277530 runs 0x27EFF0(u16 cd+0x58) and erases the record (0x281E40 -> 0x281130 -> 0x280DA0), then does inc u16 [cd+0xA78] NumberOfWonRaces.
   - Keep the record in the list until then: 0x277530 has no -1 check either.

8. No win: remove the record so the partner's save does not keep a foreign race.
   - Find its index k by id.
   - If it is the last one, set [cd+0xA60] -= 0x4C.
   - Otherwise memmove records k+1..n-1 down by 0x4C, then end -= 0x4C. Optionally write 0x473E44 into the freed slot's +0x00.
   - Undo step 5 if it was done.
   - Do this before the partner's autosave (race state 11) serialises careerData.

What keeps the save valid:
- UniqueId must be unique within the partner's open and put-aside lists, and must come from the partner's own counter cd+0xB18.
- City and RaceIdx index the static DB [0x557EE4] (City*0x50; defs at +0x20, stride 0x30). It is the same binary, so they stay valid.
- City should be the partner's current city: 0x2806F0 overwrites cd+0x50 and cd+0x58 with the record's city.
- HookmanIdx and SideQuestIdx must refer to things the partner has open, or be -1.
- Task* must be the partner's own pointer or 0.
- The serializer 0x27D770 saves +0x1C and +0x1E as names through static tables, and +0x20 as the task name string. The loader 0x27D590 re-resolves them, and an unknown task name only prints a debug message (0x473F90) and stores 0.

MARKERS: yes. The cruise race object (vtable 0x46A7C8, ctor 0x1D6D70, careerData at +0x1320) has update method vtbl+0x44 = 0x1D8F20 (called at 0x1EE674). Each call it walks the live open list from begin/end. For every record with City == [[0x53F2E0]+0], it places a start marker through 0x1D71C0 when:
- HookmanIdx == -1 (or that hookman is present or being chased), and
- SideQuestIdx < 0 (or equal to the current side quest), and

RECIPE: CONCLUSION: you cannot call guest functions from the mod's own thread using only data writes. All guest threads share one global register file, and only one guest fiber runs at a time, so a second OS thread writing esp/ecx and calling native code would race with the game. Patching the 24-byte .rdata table is also not a reliable way to redirect virtual calls, because every icall site keeps its own resolved-target cache in .data. There is a safe route that needs no patching at all: the mod's existing xinput1_4 proxy (ProxyXInputGetState -> mod::game::Pad) already runs on the game fiber, synchronously inside guest code. The HLE XInputGetState (0x1404DE2F0) and HLE XGetDeviceChanges (0x1404DD940, called inline from guest 0x84C00) both call 0x1404E3510, which calls XINPUT1_4 ordinal 2 (IAT 0x1425756D0). The full guest register file is live in globals at that moment. So the proxy is a per-poll hook on the game thread, and guest functions can be called from it.
