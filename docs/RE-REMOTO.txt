==================== remote-input
ANSWER: SHORT ANSWER
mcPlayerInput does not have one flag that picks pad vs. network. The choice comes from three gates.
(1) Is an input object created at all? 0x2CB320 creates it only if the slot's pad port is not -1 OR the race is a network game.
(2) Does the object have a local pad? Update 0x2C9AA0 takes the pad path only if input+0x08 != -1, input+0x0A (pad port) != -1 and input+0x64 (pad mapper) is not NULL.
(3) 0x2C9570 runs at the end of every Update path and only does anything when setup+0x108 != 0.
  - If 0x2694B0() (setup+0x3D8, the local network slot) == input+0x60 (the player slot), this is the LOCAL player. Its own controls are packed into input+0x6C..+0x77 and +0x78 is set to 1. The packed bytes are then decoded and applied back to its own car.
  - Otherwise this is a REMOTE player. If input+0x78 == 0 nothing happens. If it is non-zero, the packet is decoded and written into the car.
In a network game the pad path also skips its own write to the car (0x2CA4B2 calls 0x2694A0 and jumps to 0x2CA60C), so even the local car is driven through the quantized packet.
Session [0x557EFC] is not read by Update or 0x2C9570. It is used only on the send side (0x2C188C: session+0x10 >= 0 and session+0x24 != 5, then vtable+0xD4) and in remote correction (0x2C055A: vtable+0x18).

RECEIVE PATH
- Dispatcher 0x1AF470 switches on msg[0]-0x40 through jump table 0x1AF6F4 and calls the session object's vtable. vtable 0x449100: +0x170 / +0x184 / +0x188; base vtable 0x466518 at 0x1AF1E2.
  - msg 0x40 goes to 0x24C70: input only.
  - msg 0x41 goes to 0x24CC0: state only.
  - msg 0x42 goes to 0x26D00: input and state. Message size 0x40; ctor 0x1AD170; layout: +0x08 = 12-byte input, +0x14 = 0x2C-byte state.
- Each handler is called as (msg, senderSlot) and ignores senderSlot == 0x2694B0().
- The handler finds the input as players[slot] -> +0x14 (vehicle holder) -> +0x04 (mcPlayerInput) and calls 0x2C9810(msg+8).
- 0x2C9810 copies 3 dwords into input+0x6C/+0x70/+0x74 and sets byte input+0x78 = 1.
- The remote side never clears +0x78. The last packet stays latched and is re-applied every frame. Only the sender clears it after a send (0x2C9830).

PACKET LAYOUT (12 bytes at input+0x6C)
- +0x6C dword flags: the low 24 bits are copied to input+0x28 (the button bits).
  - 0x100 = upshift: transmission 0xADAC0 on [car+0x14].
  - 0x200 = downshift: 0xADAF0.
  - 0x02 calls 0xF6BD0 on holder+0x0C. 0x40 calls 0x10B2C0 on holder+0x10. 0x04 calls 0x1113F0 on car+0x184. 0x08 calls 0x128E50 on car+0x180.
  - 0x10 together with the high byte +0x6F: the receiver sets [holder+0x44]+0x3C = byte-1, then clears bit 0x10 and the high byte, so this one is one-shot. Bit 0x20 is its argument (0x101A10).
  - 0x8000 and 0x10000..0x100000 feed car+0x18C (0x2C8C40).
- +0x70 u8 throttle = (int)(throttle*255); decoded *1/255.
- +0x71 u8 brake, same scaling.
- +0x72 u8 handbrake, same scaling.
- +0x73 s8 steer = (int)(steer*127); decoded *1/127. Truncated, not rounded.
- +0x74 u8 gear = input+0x2C (current gear read from [[car+0x14]+0x14]). The receiver only stores it back in input+0x2C; it does not set the car's gear. Gear changes on a remote car happen only through flags 0x100/0x200.
- +0x75 and +0x76: s8 copies of input+0x20 and +0x24 (two extra axes) *127.
- +0x77 s8 = input+0x54 (transmission/assist mode bits, passed to 0x1210F0 on the car).
- After decoding, 0x2C9570 writes the car (car = input+0x34 = holder+0x08): car+0x6C steer, +0x70 throttle, +0x74 brake, +0x78 handbrake, +0x7C = input+0x1C. +0x1C is not in the packet. It then calls 0x2C8C40.
